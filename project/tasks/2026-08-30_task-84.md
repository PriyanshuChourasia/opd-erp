# TASK 84 — Define Common OPD Report API Convention

## Status: ✅ Complete

## Overview

This document defines the common API convention for all OPD (Outpatient Department) reports. The convention ensures consistency across all report endpoints, making them predictable for frontend implementation and easier to maintain.

---

## 1. API URL Structure

### Base Path
```
/api/reports/
```

### Endpoint Naming Convention
```
GET /api/reports/{report-name}
```

**Rules:**
- Use kebab-case for multi-word report names
- Use nouns, not verbs (e.g., `appointment-summary` not `get-appointments`)
- Be descriptive but concise
- Prefix related reports with the domain (e.g., `appointment-*`, `revenue-*`)

## 2. HTTP Method

All report endpoints use **`GET`** method.

**Reasoning:**
- Reports are read-only operations
- No data mutation occurs
- Results can be cached by HTTP proxies/CDNs
- Bookmarkable/shareable URLs

## 3. Query Parameters

### Common Parameters (All Reports)

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `from` | string (ISO date) | No | Varies by report | Start date (inclusive) |
| `to` | string (ISO date) | No | Varies by report | End date (exclusive) |

**Date Format:** `YYYY-MM-DD` (ISO 8601)
- Example: `2026-08-30`

**Default Date Ranges:**
- Daily reports: Today
- Weekly reports: Last 7 days
- Monthly reports: Current month (1st to today)
- Trend reports: Last 30 days

### Report-Specific Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `doctorId` | string (UUID) | No | All doctors | Filter by doctor ID |
| `patientId` | string (UUID) | No | All patients | Filter by patient ID |
| `status` | string | No | All statuses | Filter by status |
| `type` | string | No | All types | Filter by type (e.g., CONSULTATION, FOLLOW_UP) |
| `paymentMethod` | string | No | All methods | Filter by payment method (CASH, CARD, UPI) |
| `paymentStatus` | string | No | All statuses | Filter by payment status (PAID, PENDING, PARTIAL) |
| `departmentId` | string (UUID) | No | All departments | Filter by department |
| `specialization` | string | No | All specializations | Filter by doctor specialization |
| `limit` | number | No | 10 | Limit results (for top-N reports) |
| `page` | number | No | 1 | Page number for pagination |
| `pageSize` | number | No | 20 | Items per page |

### Example Query Strings

```
# Daily appointment summary for today
GET /reports/daily-appointment-summary

# Doctor performance for last 30 days
GET /reports/doctor-performance?from=2026-08-01&to=2026-08-31

# Revenue for specific doctor
GET /reports/revenue-summary?from=2026-08-01&to=2026-08-31&doctorId=abc-123

# Payment collection for Card payments
GET /reports/payment-collection?from=2026-08-01&to=2026-08-31&paymentMethod=CARD

# Top 20 medicines
GET /reports/medicine-usage?from=2026-08-01&to=2026-08-31&limit=20
```

## 5. Pagination Strategy

### When to Paginate
- **Summary/aggregate reports:** No pagination (return all aggregated data)
- **Detail lists with > 100 records:** Use pagination
- **Top-N reports:** Use `limit` parameter (no full pagination)

### Pagination Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `page` | number | 1 | Page number (1-indexed) |
| `pageSize` | number | 20 | Items per page (max: 100) |

### Pagination Response

```typescript
{
  "pagination": {
    "page": 1,           // Current page
    "pageSize": 20,      // Items per page
    "totalPages": 8,     // Total pages
    "totalRecords": 150, // Total records matching filters
    "hasNext": true,     // Has next page
    "hasPrevious": false // Has previous page
  }
}
```

### Pagination Calculation
```typescript
totalPages = Math.ceil(totalRecords / pageSize)
hasNext = page < totalPages
hasPrevious = page > 1
```

## 8. Caching Strategy

### Cache Headers

| Report Type | Cache-Control | Reasoning |
|-------------|---------------|-----------|
| Real-time (today) | `no-cache` | Data changes frequently |
| Historical (past 7 days) | `max-age=300` (5 min) | Changes less frequently |
| Historical (past 30 days) | `max-age=3600` (1 hour) | Rarely changes |
| Historical (past year) | `max-age=86400` (1 day) | Static data |

### ETag Support

```http
HTTP/1.1 200 OK
ETag: "abc123"
Cache-Control: max-age=300
```

### Backend (Service)

```typescript
// reports.service.ts

async getDailyAppointmentSummary(
  from?: string,
  to?: string,
  doctorId?: string,
) {
  const start = from ? new Date(from) : startOfDay(new Date());
  const end = to ? new Date(to) : startOfDay(addDays(new Date(), 1));

  // Validate date range
  if (start >= end) {
    throw new BadRequestException('Invalid date range: from must be before to');
  }

  const where: Record<string, unknown> = {
    date: { gte: start, lt: end },
    deletedAt: null,
  };
  if (doctorId) where.doctorId = doctorId;

  // Query database
  const appointments = await this.prisma.appointment.findMany({ where });

  // Process and return
  return {
    success: true,
    data: {
      summary: { /* computed metrics */ },
      byDoctor: [ /* grouped by doctor */ ],
      byType: [ /* grouped by type */ ],
      trend: [ /* daily trend */ ],
    },
    meta: {
      from: start.toISOString().slice(0, 10),
      to: end.toISOString().slice(0, 10),
      generatedAt: new Date().toISOString(),
      filters: { doctorId },
    },
  };
}
```

### Frontend (API Call)

// reports/data/api.ts

export async function fetchDailyAppointmentSummary(
  from?: string,
  to?: string,

  if (from) params.set('from', from);

  const res = await apiFetch<{

    data: DailyAppointmentSummaryData;
    meta: ReportMeta;
  }>(`/reports/daily-appointment-summary?${params}`);
  
  return res.data;
}

## 12. Validation Rules

### Date Validation
- `from` must be a valid ISO date string (YYYY-MM-DD)
- `to` must be a valid ISO date string (YYYY-MM-DD)
- `from` must be before `to`
- Maximum date range: 1 year (365 days)

### ID Validation
- `doctorId` must be a valid UUID if provided
- `patientId` must be a valid UUID if provided
- IDs must exist in the database

### Numeric Validation
- `limit` must be between 1 and 100
- `page` must be >= 1
- `pageSize` must be between 1 and 100

### String Validation
- `status` must be one of the valid enum values
- `type` must be one of the valid enum values
- `paymentMethod` must be one of: CASH, CARD, UPI

## 13. Summary

### Key Conventions

| Aspect | Convention |
|--------|------------|
| **URL Structure** | `GET /api/reports/{report-name}` |
| **Date Format** | `YYYY-MM-DD` (ISO 8601) |
| **Response Wrapper** | `{ success, data, meta }` |
| **Pagination** | `{ page, pageSize, totalPages, totalRecords, hasNext, hasPrevious }` |
| **Summary** | Always include key metrics in `data.summary` |
| **Errors** | `{ success: false, error: { code, message, details } }` |
| **Caching** | Varies by data freshness (no-cache to 1 day) |
| **Rate Limiting** | 50-100 req/min depending on complexity |

### Benefits

1. **Consistency** — All reports follow the same pattern
2. **Predictability** — Frontend can reuse code across reports
3. **Maintainability** — Easy to add new reports
4. **Testability** — Clear contract for testing
5. **Documentation** — Self-documenting API structure
